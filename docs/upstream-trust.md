# Upstream trust roots

Every image and binary we pull at build time has one of three trust
levels. This document spells out which is which and why.

## 1. Cosign-verified at the publisher's identity

These images are signed by their publisher via cosign keyless against
the public Sigstore Rekor transparency log. We `cosign verify` them
on every push (`.woodpecker/verify-upstream.yml`).

| Image | Publisher identity | OIDC issuer |
|---|---|---|
| `gcr.io/projectsigstore/cosign:v3.0.6` | `keyless@projectsigstore.iam.gserviceaccount.com` | `https://accounts.google.com` |
| `docker.io/aquasec/trivy:0.71.2` | `https://github.com/aquasecurity/trivy/.github/workflows/...` | `https://token.actions.githubusercontent.com` |

A signature mismatch on any of these fails the pipeline. This catches
the case where a registry serves different bytes under the same digest
(rare but real - cf. the trivy supply-chain incident of march 2026).

The cosign image is the **bootstrap**: we trust it at the digest pinned
in `versions.env` and `.woodpecker/*.yml`. From inside that pinned
cosign, we verify everything else (including cosign itself, against
its publisher identity).

Local verification before a digest bump:
```bash
tools/verify-upstream.sh           # all known images
tools/verify-upstream.sh trivy     # one image
```
The script uses an interactive shell so it expects to run on a
workstation - the CI uses the inline commands in
`.woodpecker/verify-upstream.yml` instead (the cosign image itself is
distroless and has no shell).

## 2. Pinned-digest only

These are pulled via tag-and-digest like `python:3.12-slim@sha256:46cb7c...`
The publisher does NOT individually cosign-sign these images, so the
pinned digest is the trust root.

| Image | Why digest-only |
|---|---|
| `docker.io/library/python:3.12-slim` | Docker Library images aren't cosign-signed by Docker Inc. |
| `docker.io/library/nginx:stable-alpine` | Same. |
| `docker.io/library/rust:1-slim` | Same. |
| `docker.io/library/postgres:18-trixie` | Same. |
| `docker.io/library/alpine:3.23` | Same. |
| `docker.io/library/docker:29-cli` | Same. |
| `docker.io/anchore/syft:v1.42.3` | Cosign discovers a `.sig` artifact next to the image but cannot validate it against the public Rekor log - Anchore doesn't publish syft image signatures to the public transparency log. The pinned digest is the only trust root. |

For these, mutation detection relies on:
- Docker Hub's content-addressable storage (digest is integrity-bound)
- TLS at pull time (in-transit)
- Our own pin in `versions.env` (refusing to fall back to tag)

A registry compromise that replaces the underlying blob would change
the digest; our pin would then refuse the pull (`docker pull` fails on
digest mismatch). What it CANNOT detect is a registry fully
substituting both image AND our pin reference (i.e. an attacker
controlling both the registry and our git repo).

## 3. Hash-verified Python deps

`pip install --require-hashes -r api/requirements.txt`
refuses any wheel/sdist whose SHA-256 isn't in `requirements.txt`.
Since `requirements.txt` is generated by `pip-compile --generate-hashes`
and committed, a PyPI mirror swap would fail the build.

## 4. Locked Cargo crates

`cargo build --locked` against `api/rust/Cargo.lock` and
`agent/rust/Cargo.lock` fixes every transitive dep at a
specific version + checksum, refusing to update the lockfile during
build. Crates.io mirror swap -> build fails.


## Bumping a verified upstream

When upgrading any image in column 1 (cosign-verified):

1. `tools/pin-digests.sh image:newtag` to resolve the new digest.
2. Update `versions.env` and every `.woodpecker/*.yml` reference.
3. Update `.woodpecker/verify-upstream.yml` and `tools/verify-upstream.sh`
   if the publisher's identity / issuer changed.
4. Run `tools/verify-upstream.sh` locally - must pass before commit.
5. Push. CI re-verifies in `.woodpecker/verify-upstream.yml`.
